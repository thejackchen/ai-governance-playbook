# 新校验先影子跑，再生效（5 个自身 bug 换来的结论）

- **来源**：微信客服 · 一夜给应答链路加 9 类产品属性校验，全部默认影子模式（只记录不拦截）。
- **场景**：给真实流量加拦截型规则（内容校验 / 风控 / 参数校验 / 反作弊 / 告警阈值）。上线前测试全绿，作者认为可以直接生效。
- **执行者做法**：本地回归绿了就切生效；或图省事把新规则默认设成拦截，"反正测过了"。
- **实际发生**：一夜之内自己写的规则被抓出 **5 个 bug**——4 个本地回归抓的（正则边界断言漏掉真错配的原文写法、把型号里的连字符数字当区间、豁免序号导致"单价 1 元"被放过、匹配方向写反漏掉整类型号），**第 5 个是影子模式在生产真实语料上抓的**：客户把 `C25 30MA` 写成 `C2530MA`（无空格连写），被解析成 2530mA 并误判冲突。**若当时是生效模式，这条真实客户消息会被误拦。**
- **负责人要的做法**：
  1. 新校验**默认影子**（只记录不改判），该默认值写进回归测试锁死，防止后人"顺手"改成生效；
  2. 影子必须**落盘可统计**——不落盘等于没跑，且给虚假安全感；
  3. 切换**靠数字不靠感觉**：日统计看拦了多少、什么冲突、有无误伤，逐条核对后才切；
  4. 代价不对称时**宁可漏不可错杀**，并设计「不确定就不判」的退出路径（本次用了 4 次：属性缺值 / 连写歧义 / 多字段指代歧义 ×2）。
- **可泛化边界**：因果机制与项目无关——**作者写规则时脑中的输入分布来自自己想象的样例，真实分布来自成千上万个不受约束的人**；两者的差集恰恰是最不规则的样本，且**不出现在任何设计文档、测试用例或需求描述里**。故校验规则的正确性无法在上线前被证明，只能被真实流量证伪。不适用于纯内部计算（无外部输入分布）或已有完备形式化规范的场景。
- **载体**：判例先行；可下沉的机器件 = 代码评审检查项「新增拦截型规则的默认值是否为影子 + 是否有统计出口」。
