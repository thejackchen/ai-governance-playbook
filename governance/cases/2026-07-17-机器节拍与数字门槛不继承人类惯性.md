# 机器节拍与数字门槛不继承人类惯性

- **来源**:产品中心(母版)· 2026-07-17 · 同日两例同族,负责人两次当场纠正
- **场景**:①AI 为「判例提炼进 playbook」设了「≥2 个项目出现」的数字门槛;②AI 给纯机器执行的知识库语义 lint 排「每周一 09:00」节拍。
- **执行者做法**:沿用为人设计的形式(可数门槛、周报节拍),因为「看起来像制度」。
- **负责人要的做法**:①「一个项目提炼出来的东西就不好吗?你这个形式化是哪里来的?」——升级判据 = 因果机制是否普适,不数出现次数;②「有了 API 为什么不每天?非要问题越积越多?」——机器维护成本趋近零,日结不积压。
- **可泛化边界**:节拍与门槛跟着**消费者/执行者**走——执行者是机器/LLM,频率按成本与时效算、准入按机制分析;消费者是人,才按注意力预算设计(如「待拍板清单 ≤10 项」保留,因为读者真的是人)。周报、季审、行数预算、可数门槛这类形式脱离服务对象仍会自我复制,是形式主义高发机制。等第二个项目再掉一次坑才收编,违背 playbook 存在的目的。
- **载体**:已下沉全局会话协议第 7 条(负责人本机,每会话注入)+ 个人知识库同名判例(证据链,负责人本机)。

## 后续实证:定时对账单在母版死亡(2026-08-01)

- **事实**:母版(产品中心)按 v2 对齐安装的周治理对账包(GitHub Issue,周/月/季/年四档节拍)运行两期(#4 07-20 / #5 07-27),**两期零人类互动**——负责人不知道它存在。负责人当面裁决:「这种有时间的对账单,后面都让我们升级成 hooks 或者这种硬的指标,不用、不靠这种东西,这种东西一点用都没有。」原「8 期零互动→删」死亡条件在 2/8 处提前应验。
- **升级形态**:workflow 删除,读数硬化为 SessionStart 单行「治理脉搏」(governance-pulse.mjs:队列滞留/事故未闭环/流量对账/待决缺口,⚠ 由 AI 在对话里当面报负责人)——「被读」从「负责人想起来去 GitHub」改绑「开工事件」,与判例〔自动账本活手写账本死〕的机制判据(读写动作绑定必然发生的触发事件)一致。落点=产品中心 decision 053。
- **对模板的含义**:setup.md「心跳定时器」步骤(workflow schedule/等效 cron)按本实证应改为事件驱动 pulse 形态——「对账单生成了」不等于「对账发生了」,消费端(负责人注意力)不存在时,定时生产只是形式主义的自动化。v3.3.1 候选在途,本次只补判例不动模板,模板改造留 playbook 侧线程按此执行。
