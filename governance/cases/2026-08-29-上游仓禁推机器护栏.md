# 上游仓禁推要用机器护栏，不靠 agent 记忆

- **来源**：AIOS 微信客服 Demo5 · 2026-08-29 · 负责人当场纠正
- **场景**：WoC（WechatOnCloud）工作区的 `origin` 指向第三方官方上游仓，本地干线分支承载私有补丁（surface 定制、部署钉扎），从未也不应外推；执行机（Mini）取码走本地构建产物投放，不走 GitHub。
- **执行者做法**：主 agent 在该仓提交后，惯性套用「提交即推远端」纪律执行了 `git push origin <干线分支>`，被 GitHub 以 403（无写权限）拒绝，未造成实际泄漏。若恰好持有上游写权限（如维护者本人操作），同一动作就是把私有补丁泄漏进官方仓的真实事故。
- **负责人要的做法**：推送前先核验远端语义——「提交后推远端」隐含假设「远端是我们自己的协作线」，远端是上游时同一动作语义反转为泄漏。发现即堵死：当场 `git remote set-url --push origin DISABLED-...` 物理禁用 push（fetch 保留可追上游），并把该仓远端语义与真实发布通道写进项目 runbook 坐标表。
- **可泛化边界**：任何「远端指向第三方/官方上游」的仓库（vendored fork、补丁仓、镜像仓），第一次动它之前：① `git remote -v` 判定推送语义（协作线 or 上游）；② 判定禁推的当场禁用 push URL 作机器护栏；③ 远端语义与发布通道落项目正本供开工回读。不依赖任何 agent 的记忆或自觉。
- **载体**：AIOS 侧已落——WoC 工作区 push URL 已禁用，runbook 坐标表已钉死该仓「干线只住本地、严禁外推」；母版侧本判例即载体。
