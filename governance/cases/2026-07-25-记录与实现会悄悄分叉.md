# 记录与实现会悄悄分叉——写下"已撤掉"不等于真撤掉了(同夜两次)

- **来源**:微信客服 + llm-wiki · 2026-07-25 一夜内同一形态两次,都是自己造的。
- **场景**:文档/判例/ROADMAP 里写下的状态与数字,在实现继续变化后悄悄失真。
  - **实例①**:给 vault 加的 lint 检查三版都有假阳性,决定撤掉并写进判例。`git checkout` 执行了、没报错,但**后续一次 `git add wiki/cases/*.md` 把工作区残留的 v1 代码连带提交了**——于是"判例说已撤掉、代码跑着最不准的 v1",躺了两轮提交才被发现。
  - **实例②**:同一晚三次扩属性维度,ROADMAP 两处写"7 类语义"、能力注册表写"6 类",而代码已是 9 类;SKU 数四处写死"8.15 万"(本地首拉数),**生产因 PIM 限流实际 7.8~8.1 万且每日刷新还在变**——那个数字在生产上从来没成立过。
- **执行者做法**:执行了撤销命令就认为撤干净;改代码只改代码;在文档里写死数量/版本/状态而不标注来源与时点。
- **负责人要的做法**:
  1. **撤销/回滚后验证工作区**(`git status` + 实际读文件),不凭"命令没报错";
  2. **收尾按「本次改动涉及的事实在别处还有没有叙述」回扫**——一次回扫当场抓到七处漂移;
  3. 能改成**指针**的别写死值:"准确值查产物 `sku_count`" 优于 "8.15 万";
  4. **可精确校验的交机器对账**:数代码里的维度数与文档声称值比,warn 级不挡提交(改维度与改文档常不在同一提交)。
- **可泛化边界**:**记录是快照,实现是流**。记录在写下的那一刻为真,此后不会自己跟着变;而变更本身不会去回扫所有提到它的地方。二者分叉**没有任何自动信号**——不报错、不失败、CI 全绿。比"成功信号是假的"更隐蔽:那里至少有个信号(只是含义错了),这里连信号都没有,只有一份逐渐失真的文字。
- **载体**:微信客服 `scripts/governance-lint.mjs` 加"语义数对账"(数 `checked.append` 与文档声称值比,warn 级);判例保留作证据链。**日期命名的交接/事故类文档是时点快照,不该保鲜**——给它加保鲜是对抗设计意图,正确做法是在文中点明"当前状态以 ROADMAP 为准,冲突时信它"。
