# 改性能前先证伪指标本身（一次完全白做的修复）

- **来源**：微信客服 · 「消息检测延迟 p50 = 33 秒」长期被当作首要性能问题。
- **场景**：拿仪表盘上最刺眼的数字直接开优化。
- **执行者做法**：看到最大的数就动手；优化后指标没动就加大力度。
- **实际发生**：33 秒是**假的**——读消息的第三方 CLI 把时间戳 `strftime` 到分钟，**秒被截断**，系统按整分算，平均凭空多算 30 秒；真实延迟只有 3–4 秒（= 轮询间隔）。**代价**：此前有人据此做过一次修复，实测前 30.1s / 后 32.9s **完全无效**，白干，还用同一个坏指标"通过"了自己的验收，真问题（在查询层）被掩盖至今。
- **负责人要的做法**：动手优化前先证伪指标本身，问三件事 + 一次交叉检验：
  1. **精度**：这个时间戳的精度是多少？有没有被截断 / 取整 / 量化？
  2. **口径**：起止点各是什么事件？中间混没混进排队、重试、批处理？
  3. **时钟**：两端时钟同源吗？
  4. **自洽**：这个数字与系统里其它已知事实矛盾吗？（本次旁证：另一处回读验证 4×750ms 就能确认送达——**若落库真要 33 秒，那机制根本不可能工作**）
- **证伪手法（可直接复用）**：**把可疑指标按取值区间分桶看分布**。真实耗时必然**右偏集中**（多数快、少数慢）；**均匀分布只可能来自截断或量化**。本次实测 0–60 秒分 6 桶 = 193/285/279/289/293/260，近似均匀，当场定性。
- **可泛化边界**：适用于一切**由自己代码埋点产出的**性能/质量指标。第三方 SLA 或外部计费口径不适用（那里的问题通常是口径解释而非精度）。
- **载体**：判例先行；可下沉的机器件 = 埋点评审检查项「时间戳精度与起止口径是否写在字段注释里」。
