# 发布控制面必须自证运行身份与安装版本

- **来源**：AIOS 测试发布 · 2026-07-29 · 发布事故复盘与本地防线复验
- **场景**：接续发布时，操作者先在错误机器做了只读检查；正确测试机的 migration release 位于另一文件系统而空间耗尽；仓库中的 worker 与服务器安装件漂移；同名容器因 Compose project 已变更而无法重建。表面上是四个问题，实际都是把“候选代码”误当成完整发布上下文。
- **执行者做法**：只凭仓库脚本、一个部署路径的可用空间、容器名或旧日志判断目标正确；把 root 日志可读当作协作者已收到失败反馈。
- **负责人要的做法**：任何人工接管、排障或发布先读回 `host + user + deploy root + target SHA`；分别核对控制面安装版本、所有重写路径的真实 filesystem，以及运行对象的 Compose project/service/labels。未知归属一律 fail-closed，失败必须回到提交者实际使用的协作面。
- **可泛化边界**：适用于所有“仓库代码 + 服务器安装 worker + 多挂载 + 容器编排”的发布系统。应用提交、控制面安装件、存储目标与运行对象是四个独立身份；任一项只由路径名、同名容器或仓库文件推断，都会造成“代码正确但执行错位”的假绿。
- **载体**：项目发布 runbook 固化四元组读回；worker 输出 installed/requested SHA、逐写入路径容量检查、已知历史归属兼容和未知归属拒绝；自动测试覆盖非标准目标、陈旧配置和低容量的提前失败。提交/MR 状态回写仍须由协作平台的 exact-SHA 门禁实现，日志权限不能替代反馈通道。2026-08-16 产品中心再次实证同一机制：多 worktree 与未提交改动、错误项目配置、调试端口与 CLI 端口、shell exit `0` 与正文错误被混为一个“发布环境”，导致长时间寻找正确入口。项目侧应把这些具体身份固化到本地 runbook 和 wrapper；上游只维护[发布治理合同](../../docs/release-governance.md)，不保存项目路径或平台参数。
