# 多 worktree/多 AI 并发同仓的 git 卫生(7 次复现,已升源头治理)

- **来源**:产品中心+AI-OS · 4 个独立 session 各自付过代价 + 同日再犯 2 次;**2026-07-25 微信客服第 7 次,且是更根本的形态**。
- **场景**:多执行者并发同一仓库。
  - **旧形态(提交卫生)**:commit 时把并行线程的未完成工作「顺手」带进提交(CHANGELOG/index 类高频公共文件最易中招);cd 后复合命令在错误目录执行。
  - **新形态(派活即错,2026-07-25)**:同时派 4 条实现车道**全部指向同一个物理 checkout**。后果是提交卫生管不住的:车道互相 `git checkout` 切分支(HEAD 运行中被改 6+ 次)、抢 `.git/index.lock`(一条车道代码写完验证全绿却**提交不上**)、另一条自己逃进 worktree 才得以落地。**最贵的一笔在收尾**:清场时把 `tests/eval_intent.mjs` 当成重复副本整个丢弃,**连带删掉了另一条车道写在同一文件里的 6 个回归用例**——代码上了生产、配套金标没上,正是「改代码前先有金标」要防的事。
- **执行者做法**:`git add -A` 图省事;脚本不锚定绝对路径;**派并发车道时不做隔离,赌「各车道改的文件不重叠」**。
- **负责人要的做法**:
  1. **派活即隔离**:每条并发车道开自己的 `git worktree`,派活时就指定,不靠车道自觉(同一晚对照实验:用了 worktree 的车道全程零冲突);
  2. commit 前逐文件 diff 确认改动来源;
  3. 并发期永不 `git add -A`(或 add 后 `restore --staged` 排除清单);
  4. 脚本一律绝对路径或 `git -C`;
  5. **清场遇到「同一文件被多方改过」时按内容归属逐段确认,禁止整文件丢弃**。
- **可泛化边界**:暂存区是共享的,意图不是——一切多执行者共享工作区场景成立(7 次复现,跨项目跨模型)。**"文件不重叠"不是安全论证**:git 的分支/索引/HEAD 是全局的,不按文件分区。**最危险的不是冲突本身,而是冲突把损失推迟到收尾**——彼时人已疲劳、上下文模糊,最容易误删正确的东西。
- **载体**:①**源头**:派并发车道必须带隔离参数(工具层已支持 worktree 隔离),这是本次升的载体;②待下沉 pre-commit(暂存文件与声明范围核对);③判例保留作证据链。
