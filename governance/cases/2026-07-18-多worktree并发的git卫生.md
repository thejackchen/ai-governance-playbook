# 多 worktree/多 AI 并发同仓的 git 卫生(8 次复现,已升源头治理)

- **来源**:产品中心+AI-OS · 4 个独立 session 各自付过代价 + 同日再犯 2 次;**2026-07-25 微信客服第 7 次,且是更根本的形态**;2026-07-29 AIOS 集成审计出现共享 checkout 下的第 8 次。
- **场景**:多执行者并发同一仓库。
  - **旧形态(提交卫生)**:commit 时把并行线程的未完成工作「顺手」带进提交(CHANGELOG/index 类高频公共文件最易中招);cd 后复合命令在错误目录执行。
  - **新形态(派活即错,2026-07-25)**:同时派 4 条实现车道**全部指向同一个物理 checkout**。后果是提交卫生管不住的:车道互相 `git checkout` 切分支(HEAD 运行中被改 6+ 次)、抢 `.git/index.lock`(一条车道代码写完验证全绿却**提交不上**)、另一条自己逃进 worktree 才得以落地。**最贵的一笔在收尾**:清场时把 `tests/eval_intent.mjs` 当成重复副本整个丢弃,**连带删掉了另一条车道写在同一文件里的 6 个回归用例**——代码上了生产、配套金标没上,正是「改代码前先有金标」要防的事。
  - **共享 checkout 的第 8 形态(2026-07-29)**:运行时明确让多代理共享同一工作树,但委派只按任务主题分工,没有把可写文件当互斥资源。同一 warehouse engine/测试面被多条实现车道处理,单车道各自测试通过,晚返回结果仍可能覆盖先前已经验修的组合态;证据计数也只能在最终文件集合上重跑后确定。
- **执行者做法**:`git add -A` 图省事;脚本不锚定绝对路径;**派并发车道时不做隔离,或在共享 checkout 中让写入所有权重叠**。
- **负责人要的做法**:
  1. **能隔离时派活即隔离**:每条并发车道开自己的 `git worktree`,派活时就指定,不靠车道自觉;
  2. **运行时必须共享 checkout 时实行单写者**:每个写代理声明独占文件列表;任何重叠文件只允许一个写代理,其余改为只读审计;代理返回顺序不是安全合并顺序,每次接收后由集成控制者重读组合 diff 并重跑组合门;
  3. commit 前逐文件 diff 确认改动来源;
  4. 并发期永不 `git add -A`(或 add 后 `restore --staged` 排除清单);
  5. 脚本一律绝对路径或 `git -C`;
  6. **清场遇到「同一文件被多方改过」时按内容归属逐段确认,禁止整文件丢弃**。
- **可泛化边界**:暂存区是共享的,意图不是——一切多执行者共享工作区场景成立(8 次复现,跨项目跨模型)。**"文件不重叠"只有在工具强制独占时才是安全合同,不能靠口头假设**;即使文件真的不重叠,git 的分支/索引/HEAD 仍是全局的。**最危险的不是冲突本身,而是冲突把损失推迟到收尾**——彼时人已疲劳、上下文模糊,最容易误删正确的东西。
- **载体**:①优先使用隔离 worktree;②共享 checkout 的单写者/独占文件合同已下沉 `pro-supervised-delivery` 委派与验收参考;③待下沉 pre-commit(暂存文件与声明范围核对);④判例保留作证据链。
