# 成功信号本身要被验证：三次假绿，机制相同

- **来源**:微信客服 · 2026-07-25 一夜内查出三起独立事故(INC-014/015/016),**共同点是"系统以为自己没问题"**。
- **场景**:系统输出了"成功"信号,人和机器都据此认为一切正常——而那个成功信号从未被验证过。三个实例:
  1. **CI 说"部署完成"**:确实完成了,但完成的是**把生产退回上一版**(远端落后时无条件 `reset --hard origin/main`)。信号真实,含义错了。
  2. **告警说"已推手机告警"**:`Promise.allSettled` 只数 `fulfilled`,而 **fetch 拿到 HTTP 400 也是 fulfilled**。信号来自"请求发出去了",不是"对方收到了"。真事故时告警通道已被免费额度打死 11.5 小时,无人知晓。
  3. **修复说"验收通过"**:06-29 一次性能修复用**同一个待验指标**验收自己,而那个指标本身是坏的(时间戳被截断)。修复前 30.1s / 修复后 32.9s,毫无改善却"通过"了。
- **执行者做法**:把"函数没抛异常""命令 exit 0""日志打印了成功"当作事情办成了。
- **负责人要的做法**:凡产出"成功"信号的地方,问三件事——
  1. **这个信号是怎么产生的**?是观测到了结果,还是仅仅"我这步没报错"?
  2. **它验证的是哪一端**?发送方视角(请求发出)还是接收方视角(对方处理了)?**跨进程/跨网络的成功必须来自对端**;
  3. **它能不能自证**?用同一套逻辑验收自己的改动 = 无效验收(实例 3);验收必须来自**独立于被验对象的证据源**。
  4. **这条"报告给人"的通路本身,有谁验证过**?——最容易漏的一问,见下方补充。
- **补充实例(同日,全在"报告给人看"的通路上)**:修完上面三个后,顺着"我写的待决事项到底有没有送到人手里"追下去,同一条通路上又是三处——① 收件箱聚合器打印"聚合 2 个项目",实则只认一种 markdown 形态,**某项目 9 条待决从未进过收件箱**(含一条"生产配置可能配错"),并把章节标题当成待决事项上报;② 每日心跳 `git commit … || true` 吞掉 pre-commit 的拒绝,报 `exit=0` 而**那天心跳一个字没落盘**;③ 桌面通知报"4 项待拍板",实际 21 项。
- **第三批(同日,执行者自己犯的)**:`npm run check` 内含的 CI 合同测试会往**临时仓**推送,输出格式与真推送**一模一样**(`da0a0fc..00826bc  main -> main`),唯一区别是上一行的 `To <url>`。执行者据此连续几轮向负责人宣称"已推双远端",实际 **6 个提交一个都没到真远端**。——**同一个动作、同样的成功输出、不同的对端**,这是本判例第 2 问("它验证的是哪一端")最纯粹的形态。修法:判据换成 `git rev-list --count <remote>/main..main`(问"远端到底有没有"),并写成 lint 的 warn 级常驻显示。
- **为什么偏偏是这条通路**:**观测设施是最少被观测的地方**——它的失效症状是"什么都没发生",而"什么都没发生"与"一切正常"从外部看完全一样。三重结构使然:① 报告通路**没有下游程序会抱怨**(真正的消费者是人,人只会以为"最近没事");② 它天天运行、天天绿,于是拿到最高信任度与最低检查频率;③ 一旦坏掉,所有依赖它的判断都失去输入,却不会有任何一处报错。`|| true` 是最典型的载体:一个"别让记账失败拖垮主流程"的合理意图,代价是把失败变得完全不可见。**正确形态不是去掉容错,是容错但出声**——不中断流程,但把失败写进日志并告警。
- **可泛化边界**:**假绿比红灯危险**——红灯至少会被看见,假绿会让人停止追问。适用于一切自动化管道:CI/CD、消息投递、批处理、监控告警、数据同步。凡"我以为它在工作"的组件,都要有一条**独立的、来自对端或旁路的存活证据**。
- **载体**:判例;可下沉的机器件 = ①投递类组件必须留"投递健康档案"(最后成功时间/连续失败数),而非只打成功日志;②管道类改动的验收证据必须与被改对象解耦;③**报告/汇报通路要有解析回归测试**——锁住"格式变了也不会静默漏项",否则漏掉整个来源都不会有人知道。
