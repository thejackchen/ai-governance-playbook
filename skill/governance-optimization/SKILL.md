# 治理优化 — 治理架构减重与验效编排器

> **v1.1**（2026-08-31；v1.0 为 AIOS 仓首跑定稿，v1.1 追加拆除战役全程落地后的四条新判例）。
> **正本在 playbook 仓 `skill/governance-optimization/`**；`~/.claude/skills`、`~/.codex/skills` 只是安装实例，改内容先改正本再同步实例。
> 定位：**只管治理层本身**——治理代码、机器门、流程文件、账本制度的减重与效果度量。全项目体检走 `project-overhaul`（那是查项目的病，本 skill 是查"查病机器"的病）。两者判例都沉 `~/llm-wiki`。

## 心法（三条铁律，判决前先背）

1. **以前存在 ≠ 合理**。治理零件都是一步步试错长出来的，试错的产物必须能被再次试错掉。沉没成本不是理由——当晚建的东西答不出判决问句，当晚删（判例：AIOS 治理面板，2026-08-30 建，同日删）。
2. **治理系统抗拆自身 = 头号红旗**。发现"删 A 会被 B 的机器门拦住"（如 kit lint 强制 installedFiles 存在），说明系统在保护自己而非保护项目——解锁链排施工序第一位。
3. **每个零件的复杂度必须由失败挣来，且只换不加**（one-in-one-out）：装新门必须同批指认可拆的旧门；答不出就不装。

## 流程

### 1. 量化盘点（数字先于观点）

- 治理代码：行数、文件数（`wc -l scripts/*.mjs scripts/governance-hooks/*.mjs ...`）
- 门的数量：doctor/lint 检查函数数（`grep -c "^function check"`）
- 慢性噪音：每次运行必刷、无人处理的 WARN 条数（警告疲劳 = 在训练所有人无视警告）
- 账本水位：认领/登记类账本总条数、未收口条数
- 开工注入税：session-start/hook 每次强制灌进上下文的字节数
- 对照物：产品代码量、根规则文件行数
- 全部记入本轮基线表，供拆后对比。

### 2. 第一性判决（逐件过堂）

每个零件只答两个问句，答不出 = 拆：

> **它防的真实失败是什么？**（要求带事故编号或真实拦截记录；30 天零拦截、零事故背书 = 收费站，不是门）
> **有没有更便宜的替代？**（git 原生能力 / 测试 / 更小的文档面。很多文档治理门的病根是文档面太大——缩文档面，门就失业）

辅助对照（业内五件套，无对应物的零件要双倍强的理由）：
① 根规则文件 ≤200 行只做路由 ② 每功能一页 spec（做什么/不碰什么/怎么算完）③ tasks/session 少数状态文件 ④ 执法只靠 pre-commit 四件套（typecheck/lint/test/防泄密）+ 测试 ⑤ 重量匹配爆炸半径（动钱/生产/数据才配重流程）。
业内铁律另记一条：**登记类制度必须依附会自死的宿主**（issue/PR/worktree/分支），宿主死登记自动死；"独立台账 + 手动销账"在任何规模下必烂（判例：claim 195 条烂账 → 生命周期焊接后自维持在个位数）。

### 3. 判决书 + 一次拍板

产出三栏：**留**（每件一句"防什么"）/ **删**（每件一句理由）/ **简化**。整份判决书让负责人**一次**过目拍板，不逐条滴灌。裁决协议：当场问、自带推荐默认与死线，沉默/取消 = 按默认执行；裁决不排队。

### 4. 分批拆除（施工纪律）

- 先拆解锁链（互锁的自保护件），再拆尸体，再拆大件。
- 一件一提交，独立可回退；每步全测试绿 + doctor/lint PASS 才走下一步。
- 拆登记类制度时**绝不删数据文件**，只改状态/停写入；真删除走人工确认。
- 共享工作区有并行会话在跑时，避开其正在写的文件；执法链大手术挑安静窗口。

### 5. 验效（拆完必测，测不过不算完）

#### 测试 A：冷启动理解考试（核心量化指标）

派 **3 个并发、零上下文**的只读 agent（同步批，不用后台模式），只告知仓库路径，考四题（各 25 分）：

1. 这个项目在做什么？当前做到哪一步？（考：能否快速找到游标/合同）
2. 你作为新实现者，开工前必须做哪些动作？先读哪三个文件？（考：Boot 路径是否可发现）
3. 有哪些不可碰的红线？（考：红线的家是否醒目、完整）
4. 怎么证明你完成了任务？（考：验收定义是否可发现、可执行）

**每个答案必须带 `文件:行` 引用，无引用不给分**（防 AI 编造好听答案）。主 agent 持标准答案卷严格评分：25=完整且引用正确；15=大体对有缺口；8=只碰到边；0=错/缺。

**阈值：平均 ≥80 且单卒最低 ≥60。** 低于阈值不许宣布优化完成——且**错题就是下一轮优化的地图**（哪题普遍丢分，哪份文档就臃肿/错位/藏得深）。

#### 测试 B：减重不减防（防砍到肌肉）

把本仓历史事故逐个重放，**留下来的门必须全部还能开火**：伪造超限膨胀文件→体量门必红；伪造密钥字符串→gitleaks 必拦；无认领改行为代码→认领门必拦；（按各仓事故簿补充）。任何一个不响 = 拆错了，回退该刀。

#### 测试 C：指标对比表

拆后重跑第 1 步全部指标，与基线并排。要求：治理代码行数/门数/慢性 WARN/开工注入税全部下降或持平，测试 A 分数不降。任何指标不降反升必须写明理由。

#### 测试 D：冷启动执行抽测（可选，重）

给一个零上下文 agent 派一件队列上的小真活，观察：它能否自己找到合同与边界？犯规时门拦住了没有？从开工到第一次正确提交的摩擦点清单，逐条归因到治理件。

### 6. 沉淀回写（skill 与治理架构共同成长）

- 本轮判例（新的"该拆的形态"、新阈值、翻车教训）**追加进本 SKILL.md**（版本号 +0.1）；跨项目认知落 `~/llm-wiki`。
- 判决书与基线/拆后对比表落目标仓正本（如 FEATURES 拆除条目），过程留 git。
- 下轮触发是**事件驱动**：负责人感到"讨论治理的时间在超过写代码的时间"、慢性 WARN 回潮、账本未收口回潮、或开新仓装治理时——不设定时任务（时间驱动的治理仪式没有一次成功过）。

## 已知判例库（首跑沉淀，2026-08-30 AIOS）

- 面板/仪表盘类 = 拉模式，没人天天看；治理信息必须推到负责人已在的地方（对话/开工播报），面板最多当按需 X 光。
- "排队等负责人裁决"必然烂尾（22-25 天无人裁是常态）：改当场问带默认死线，沉默=默认生效，队列取缔。
- 独立台账手动销账必烂 → 生命周期焊接（宿主死则登记死）。
- 治理系统机器层抗拆自身（kit lint 锁死尸体文件）真实存在，解锁链必须排第一刀。
- 冷启动考试的真正价值不在分数，在错题定位臃肿文档。
- AIOS 首跑基线（2026-08-30，拆除战役前）：3 考生平均 99（98/100/100）；开工税 = 答题前需读 8-10 个文件；铭牌仪式实证逼每个冷启动 agent 先读 lock 文件；错题：仓内无官方「当前主线」标签、session-start 与 index §0 读文顺序表述不一致。拆除后重考不得低于此线。

## 已知判例库 v1.1 增补（2026-08-31 AIOS 拆除战役全程落地）

- **拆除实绩参照**：一夜四批（worktree 登记制→git 原生、语义门→按需命令、kit 联邦→惰性铭牌、九段→四段模板），净删约 1.5k 行、doctor 15 WARN→2、开工 hook 12s→1s、全测试绿——"减重不减防"是可以一晚做完的，别拖成月度工程。
- **上游收编要过对方合同测试**：治理 kit 是带合同测试的产品，模板行为被逐字锚定；往上游灌演化版代码必须配套改其测试，改不动就回退、列 vNext 待办，不许硬闯（AIOS→playbook v4.0.0 首推 8 红即回退实证）。
- **发版仪式不是改一个字符串**：版本号有多处正本（VERSION/package.json/自托管 lock/README/CHANGELOG 头）+ kit 指纹重算，漏一处机器门必拦。这类门是"好门"的标本——它防的失败（版本与内容漂移）有真实语义，别当官僚主义拆掉。
- **共享暂存区是并发资源**：并行会话可能把你 staged 的文件顺进它的提交（AIOS d0bbf883 实证，无害但归属混淆）；多会话同库时一律 `git commit -- <path>` 按路径提交，不整体提交暂存区。
- **工具指纹失明**：认领/登记制的 agent 识别必须覆盖全部现役工具，否则主战场会话全记 unknown 且机器门不触发（Cursor 判例：修复前认领门在最常用环境整体失明）。盘点法：数一遍负责人实际在用的工具，逐个验环境指纹。
